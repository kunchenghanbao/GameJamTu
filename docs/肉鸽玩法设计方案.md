# 肉鸽玩法设计方案

## 1. 结论

现有项目可以实现这套肉鸽模式。战斗击杀结算、角色升级、装备/道具入包、技能学习、商店、场景加载和战斗胜利事件都已有基础能力；需要新增的是一层只对肉鸽 Run 生效的状态管理、奖励抽取规则、三选一卡牌界面、地图节点调度和 Boss 池。

肉鸽模式应作为独立玩法入口，不直接改写主线的等级、经验、掉落和回血规则。Run 开始时创建快照，Run 结束或失败时销毁快照，避免污染普通关卡和存档。

## 2. 推荐流程

```text
进入肉鸽入口
  -> 创建 Run 状态，随机种子固定
  -> 小地图 A（战斗）
       每击杀 1 名敌人：Run 等级 +1，并把 3 张奖励卡加入奖励队列
  -> 选择下一节点：小地图 B / 商人事件 / 休整事件
  -> 小地图 B（战斗或事件）
  -> Boss 前节点：战斗、商人或休整（三选一或二选一）
  -> 大型 Boss 战
  -> 结算：保留本 Run 结果，返回入口或开始下一轮
```

用户提出的是“每个敌人都弹三选一”。实现上仍然每杀敌生成一次三卡，但不在死亡动画、反击链或 AI 行动中立即开界面，而是进入 `rewardQueue`；当前战斗行动完全结束后逐张展示。这样不会导致敌人死亡回调重入战斗流程。若测试发现频率过高，可将弹卡条件切换为精英、每 3 击杀或小地图通关，击杀升级规则不变。

## 3. 击杀升级

### 3.1 规则

- 仅确认敌方战斗者死亡后结算，且死亡归属属于玩家队伍。
- 每次死亡只结算一次，使用战斗者唯一 ID 去重。
- `runLevel` 增加 1，同时将实际击杀角色在本次 Run 隔离副本中的等级精确增加 1；不依赖普通经验值“碰巧升级”。
- 召唤物、反伤、环境伤害需要记录 `killOwner`，归属到玩家即可升级；没有归属的环境击杀不升级。
- 达到本轮上限后，改为金币、治疗或提高下一张卡品质，避免等级继续溢出。

### 3.2 为什么不直接改敌人经验

现有经验可能同时受到伤害经验、击杀经验、多人队伍归属和等级曲线影响。给敌人配置巨量经验会产生一次多级、漏升或不同职业收益不一致的问题。肉鸽直接修改 Run 隔离副本中击杀者的等级并刷新属性，Run 结束后仍恢复主线角色等级和经验。

## 4. 三选一卡牌

### 4.1 卡牌类型

| 类型 | 选择后的效果 | 复用接口/数据 |
| --- | --- | --- |
| 主武器 | 获得一个职业可用武器实例 | `ProjectPlayer.addEquipByInstance` |
| 防具/饰品 | 获得装备实例，可带随机属性副本 | 现有装备实例与随机属性副本逻辑 |
| 主动技能 | 学习技能或提高技能等级 | `ProjectPlayer.learnSkillBySkillID` |
| 被动技能 | 添加被动效果或提高层数 | 建议以技能/状态数据承载 |
| 消耗品 | 增加药品、卷轴等数量 | `changeItemNumber` / `addItemByInstance` |
| 即时奖励 | 金币、恢复 HP/SP、升级卡品质、临时增伤 | Run 状态结算器 |

### 4.2 抽取规则

1. 使用 Run 随机种子，记录 `floorIndex`、`killCount` 和卡池版本，保证读档后结果一致。
2. 先按关卡决定品质权重，再从职业、已拥有物品和重复限制中过滤。
3. 三张尽量使用不同类型；若可用池不足，允许同类型但不能出现完全相同实例。
4. 技能不可重复时改为技能升级；装备重复时改为强化材料或金币。
5. 选中卡立即写入 Run 状态并调用现有入包/学习接口，未选卡只从本次候选中丢弃。
6. 弹窗必须支持暂停、确认、读档恢复和手柄/触屏输入；队列为空后才恢复战斗控制。

### 4.3 初始权重建议

普通小图：武器 20%、装备 25%、主动技能 25%、被动技能 15%、消耗品 15%。

精英或 Boss 前：武器 25%、装备 25%、主动技能 20%、被动技能 20%、消耗品 10%。

Boss 奖励：优先提供高品质装备、核心技能和永久 Run 强化，不重复发放低级消耗品。

## 5. 血量、技能和装备的跨图规则

### 5.1 HP/SP

推荐默认继承当前 HP/SP，不在普通小地图之间自动回满。当前世界配置的 `fullStateWhenBattleStart` 是 `true`，肉鸽入口必须保存旧值并临时设为 `false`；退出 Run 时恢复旧值。

- 普通战斗结束：保留剩余 HP/SP。
- 死亡角色：沿用项目现有最低 1 HP/离队规则，Run 结算前统一处理。
- 商人/休整：允许花金币恢复固定百分比，或提供一次有限免费恢复。
- Boss 前：建议最多恢复 30% 最大 HP/SP，不直接回满。
- Run 失败/结束：清理 Run 临时状态，再按主线规则处理角色状态。

如果设计上需要“本轮独立血条”，则在 Run 快照中保存每名角色的 `runHP/runSP`，进入地图时从快照写回；这比修改全局玩家数据更安全，但首版可直接复用项目现有角色状态。

### 5.2 技能和装备

本 Run 获得的技能、装备和消耗品应写入 Run 背包；结算时按玩法选择：

- 永久模式：写入玩家正常背包/技能表。
- 纯局内模式（推荐首版）：只存在于 Run 快照，Run 结束清空。

建议首版采用纯局内模式，避免随机奖励破坏主线经济和平衡；商人价格、卡牌品质和临时强化也只读 Run 状态。

## 6. 地图节点和场景切换

项目已有场景列表，包含普通战役、多个 Boss、野外和城镇地图。`GameGate` 负责离场事件、资源卸载、加载新场景、恢复玩家场景对象和执行新场景事件；因此不应手动销毁玩家队伍或绕过 `GameGate`。

建议增加一个肉鸽节点选择器，节点只保存场景 ID 和节点类型：

```text
RunNode {
  id: string,
  type: "battle" | "merchant" | "rest" | "boss",
  sceneID: number,
  seed: number,
  cleared: boolean,
  rewardSeed: number
}
```

切图流程：战斗胜利事件（现有公共事件 14022）完成结算 -> 写入 Run 快照 -> 显示节点选择界面 -> 选择节点 -> 调用项目原有场景切换命令/入口 -> 新场景进入事件根据 `RunNode.type` 初始化敌人、商人或休整 UI。场景切换期间暂停输入，加载完成后再恢复控制。

Run 快照至少包含：`runID`、版本、随机种子、当前节点、已清除节点、`runLevel`、金币、临时 HP/SP、卡牌/装备/技能列表、Boss 池、奖励队列和 `fullStateWhenBattleStart` 原值。

## 7. 地图池

首版不需要新建大量地图。可将已有野外/战斗场景分为小图池，将城镇场景用于商人或休整，并为大型 Boss 选择现有 Boss 场景或扩大现有战斗地图。

- 小图 A、B 从普通战斗池按种子抽取，敌人等级按 `runLevel` 和 `floorIndex` 缩放。
- Boss 前节点有概率替换为商人事件；建议 25%~35%，并设置至少一次休整机会。
- 同一 Run 内记录已用 `sceneID`，减少连续重复；地图池不足时才允许重复。
- 随机配置只决定节点和敌人组，不直接随机破坏地图碰撞、出生点和胜利条件。

## 8. Boss 是否要多个

建议至少 3 个 Boss，而不是只配置一个：

1. 高防反击型：强调防守反击、破防和近战站位。
2. 召唤控场型：召唤小怪、制造地形或限制移动。
3. 高机动范围型：远程压制、换位、阶段性移动。

每轮从 Boss 池抽取一个，同一 Run 不重复；Boss 池耗尽后才允许重复。难度优先通过技能组合、阶段机制、召唤上限和地图目标增加，不只堆生命值。后续可增加双 Boss 或随机词缀，但不建议作为首版依赖。

## 9. 与现有框架的对应关系

| 需求 | 已有能力 | 需要新增 |
| --- | --- | --- |
| 击杀检测 | `GameBattleData` 的死亡/击杀结算钩子 | 肉鸽击杀归属、去重和 Run 等级 |
| 角色升级 | `ProjectPlayer` 经验/升级体系 | 独立 `runLevel`，避免改普通经验 |
| 装备奖励 | 装备实例、随机属性副本、入包接口 | 奖励卡包装和重复转化 |
| 道具奖励 | 道具数量与实例接口 | 卡牌选择后的统一发放器 |
| 技能奖励 | 技能学习接口 | 职业过滤、重复升级、被动层数 |
| 商人 | `GUI_Shop`、商店事件指令 | Run 商店库存、价格和刷新种子 |
| 场景切换 | `GameGate`、场景切换公共命令 | 节点选择器和 Run 进入/退出钩子 |
| Boss | 现有多个 Boss 场景条目 | Boss 池、随机选择和难度缩放 |

## 10. 分阶段实现

### 阶段一：可玩的垂直切片

- Run 状态、随机种子和快照。
- 两张小图 + 一张 Boss 图固定流程。
- 击杀升一级、奖励队列、三选一卡牌 UI。
- 只发放现有武器、装备、技能和消耗品。
- HP/SP 跨图继承，商人暂用固定恢复事件。

### 阶段二：随机路线和经济

- 地图节点随机、商人概率、休整节点。
- 卡池权重、品质曲线、重复转化和商店库存。
- 读档恢复奖励队列、节点和随机结果。

### 阶段三：内容扩展

- 三个以上 Boss 原型及阶段机制。
- 被动技能层数、临时词缀、召唤物归属和精英敌人。
- 移动端适配、手柄输入、动画结束后奖励弹窗和性能测试。

## 11. 风险和边界

- 每击杀弹窗会显著打断 SRPG 节奏，必须使用奖励队列；建议保留“每击杀升级、阶段性弹卡”的可配置开关。
- 战斗胜利、场景切换和读档可能重复触发，Run 状态更新必须有事务标记和幂等 ID。
- 召唤物击杀若无归属会导致升级不一致，应在战斗者数据中保存来源角色。
- 临时装备写入正常背包会污染主线，首版必须明确纯局内或永久模式，不能混用。
- `fullStateWhenBattleStart` 是全局运行时开关，必须保存并恢复原值，异常退出也要在下次进入普通玩法时校正。
- 随机地图不能改变必要的出生点、碰撞和胜利条件；地图随机应先从经过验证的场景池抽取。

## 12. 最终建议

采用“纯局内 Run + HP/SP 继承 + 每击杀升级 + 奖励队列三选一 + 两张小图/一个 Boss + Boss 前商人概率节点”的首版方案。它最大程度复用现有项目结构，改动边界清晰，也能在后续逐步加入更多 Boss、地图、卡牌和永久解锁，而不会把肉鸽规则耦合进主线战斗。
## 13. 实施清单：窗口、脚本、数据与地图

### 13.1 必须新增的窗口

建议新增 `GUI_RogueEntry`（肉鸽入口）、`GUI_RogueMap`（节点/关卡选择）、`GUI_RogueReward`（战斗结算三选一卡牌）和 `GUI_RogueResult`（Run 结算）。入口提供开始/继续/放弃 Run 与队伍预览；节点界面显示战斗、商人、休整、Boss 节点及 Run 等级、金币、HP/SP；奖励界面固定三个卡槽，支持触屏、虚拟 A/B、暂停、奖励队列和读档恢复；结算界面负责清理临时状态。

### 13.2 可以复用的窗口

商人继续复用 `GUI_Shop`，只增加 Run 库存、价格、恢复服务和刷新适配层。经验和命中展示继续使用 `GUI_EXPReward`、`GUI_HitReward`，不要把肉鸽卡牌逻辑塞入这两个窗口。休整首版可用事件选项，稳定后再做 `GUI_RogueRest`。

每个新窗口需要在 `asset/json/ui/data/` 新增 UI 数据，在 `Game/game/project/ui/` 新建 `GUI_*.ts`，再由 UI 管理器按新 UI ID 注册。尺寸、移动端安全区和焦点顺序应固定；UI ID 以当前编辑器最大编号为准，避免占用现有战斗/商店窗口。

### 13.3 推荐新增脚本

| 脚本 | 职责 | 复用现有内容 |
| --- | --- | --- |
| `RogueRunState.ts` | Run 快照、种子、节点、临时 HP/SP、奖励队列 | 玩家数据与存档接口 |
| `RogueRunManager.ts` | 开始/继续/失败/完成 Run，保存并恢复全局规则 | `GameGate`、`WorldData.fullStateWhenBattleStart` |
| `RogueKillProgress.ts` | 击杀归属、去重、Run 等级 +1 | `GameBattleData` |
| `RogueRewardPool.ts` | 品质权重、职业过滤、三卡抽取 | 装备/技能/道具数据 |
| `RogueRewardResolver.ts` | 发放选中的卡牌、重复转化 | `addEquipByInstance`、`learnSkillBySkillID`、`changeItemNumber` |
| `RogueSceneDirector.ts` | 初始化战斗、商人、休整和 Boss | `GameGate`、场景进入事件、`GameBattle` |
| `RogueBossPool.ts` | Boss 随机、同轮去重、阶段词缀 | 现有 Boss 角色/场景 |
| `RogueSaveAdapter.ts` | Run 快照序列化、版本迁移、幂等恢复 | 现有保存/读取管理器 |

不要把肉鸽逻辑全部加入 `ProjectGame.ts` 或 `GameBattle.ts`，否则会影响主线和普通战斗。

### 13.4 推荐新增数据

新增 `customRogueCardData.json`、`customRogueNodeData.json`、`customRogueBossPool.json`、`customRogueEnemyGroup.json`（也可落入现有自定义模块列表）。卡牌字段至少包括 `cardID/name/type/quality/weight/allowedClassIDs/duplicatePolicy/effectPayload/iconID`；效果载荷只保存数值、状态 ID、装备 ID 等结构化参数，不保存可执行脚本。

Run 快照至少包含：`schemaVersion/runID/seed/floorIndex/nodeID/runLevel/gold/partyHP/SP/temporaryCards/temporaryEquipments/temporarySkills/rewardQueue/visitedScenes/usedBossIDs/worldRuleSnapshot`。读取时缺失内容应转化为金币/材料，不能令整个存档失效。

### 13.5 地图建议

建议新建 3~5 张肉鸽专用底图，首版只放地块、碰撞、玩家/敌人出生点、胜负条件和场景进入事件，不填充完整美术：小型近战图、小型开阔图、商人/休整安全图、Boss 大图和可选精英图。怪物先引用已有 Actor 和敌人组，后续再增加专用怪物与装饰。

可以复用主线地块资源，但不建议直接复用主线场景 ID：主线地图绑定剧情事件、对象开关和固定胜利条件，随机换怪可能触发剧情或破坏开关。肉鸽地图应有独立场景 ID、事件和战斗目标。

地图检查：手机镜头不遮挡出生点；玩家和敌人各有至少两套安全出生点；无不可达格和孤立目标；小图只派发肉鸽结算；Boss 预留二阶段/召唤区；商人图不启动战斗控制器，离开按钮返回节点选择。

### 13.6 具体落地顺序

1. 实现 Run 状态、随机种子、保存/恢复和 `fullStateWhenBattleStart` 原值恢复。
2. 新建入口和节点界面，用固定节点打通进入流程。
3. 新建三选一卡牌界面，验证暂停、确认、奖励队列和读档。
4. 接入击杀升级和奖励池，先只支持现有装备、技能、道具。
5. 新建两张小图和一张 Boss 底图，用固定敌人组打通一轮。
6. 接入商人/休整节点、随机地图和 Boss 池。
7. 最后补美术、移动端布局、动画、更多卡牌和永久解锁。

每一步保留独立测试入口；肉鸽入口、普通主线入口和读档入口分开验证，避免主线存档被临时奖励污染。

## 19. 与原有关卡的隔离要求

肉鸽必须是“共用底层引擎、独立玩法状态”的模块。玩家从原有关卡入口进入时，系统不创建 Run、不读取肉鸽节点、不弹出三选一卡牌；只有点击肉鸽入口卡片并确认后，才将 `RogueRunManager.active` 设为 `true`。

### 19.1 状态隔离

肉鸽状态统一存放在独立的 `RogueRunState` 中，不直接复用或覆盖主线关卡变量。至少隔离以下字段：

- Run 等级、击杀数、层数、节点和随机种子。
- 肉鸽临时金币、临时装备、临时技能、被动层数和消耗品。
- 肉鸽当前 HP/SP、奖励队列、已用地图和 Boss 池。
- 当前肉鸽模式、规则版本和进入前的世界配置快照。

普通角色正式等级、普通经验、主线装备、主线金币和剧情开关不应被肉鸽过程直接写入。首版建议所有卡牌奖励只写入 Run 临时背包；允许带出主线的内容必须经过单独的 `RogueSettlement` 白名单。

### 19.2 战斗奖励隔离

击杀结算入口必须先判断模式：

```text
if RogueRunManager.active:
    肉鸽击杀升级 + 奖励队列
else:
    原有经验、金币、掉落和装备逻辑
```

肉鸽逻辑不得无条件修改 `GameBattleData` 的普通奖励结果。普通关卡不能触发肉鸽等级 +1、三选一卡牌或肉鸽品质权重；肉鸽中的环境击杀、召唤物击杀和反伤击杀也必须先经过归属与去重检查。

### 19.3 等级和技能隔离

“每杀一个敌人升一级”同时增加 `runLevel` 和实际击杀角色在 Run 隔离副本中的 `lv`，不补普通经验，也不修改主线快照。肉鸽技能应记录在 Run 技能列表中；重复技能转换为 Run 内升级或强化，不调用主线忘记/替换技能流程。若未来允许技能带出，必须在结算阶段复制为合法的主线数据，而不是在战斗中直接写入。

### 19.4 装备、道具和金币隔离

奖励解析器应先写入 Run 背包，再由界面刷新显示。不得在卡牌生成阶段直接调用主线背包接口，避免玩家未确认选择时就获得物品。推荐的生命周期是：

```text
生成候选卡 -> 只读预览
  -> 玩家确认 -> 写入 Run 背包
  -> Run 结束 -> 清理，或由白名单结算到主线
```

商人价格、刷新次数、恢复费用和肉鸽金币均为 Run 数据。普通商店库存和主线金币不因肉鸽交易改变。

### 19.5 全局运行时配置隔离

`WorldData.fullStateWhenBattleStart` 等全局运行时设置必须使用快照恢复：

1. 进入 Run 前保存原始值。
2. 仅在 `RogueRunManager.active` 期间应用肉鸽规则。
3. Run 胜利、失败、放弃、读档失败和异常退出都执行恢复。
4. 恢复动作必须幂等，重复执行不会改变普通规则。
5. 下一次进入普通关卡前再次校验，发现仍处于肉鸽状态时先清理。

不得直接修改世界配置 JSON 作为肉鸽开关，也不得依赖某一个胜利事件才能恢复配置。

### 19.6 存档隔离

普通存档和 Run 快照分开保存。普通存档只保存正常主线所需数据；Run 快照保存肉鸽临时状态和进入前配置快照。读档入口按类型分流：

- 读取普通存档：强制 `RogueRunManager.active = false`，清理残留临时状态。
- 继续 Run：先校验 Run 版本、数据 ID 和节点状态，再恢复肉鸽场景。
- Run 快照损坏：保留普通存档可读性，提供放弃 Run 或回退到最近节点的选项。

战斗胜利、奖励选择和场景切换写入 Run 状态时要使用唯一事务 ID，防止重复触发造成重复卡牌、重复金币或重复升级。

### 19.7 场景和事件隔离

肉鸽可以复用 `GameGate` 的底层场景加载，但节点选择、敌人初始化、商人事件和奖励结算由 `RogueSceneDirector` 管理。肉鸽场景不应直接挂接主线剧情事件、主线任务开关或普通关卡结算事件。

现有公共事件（例如战斗胜利事件）如果必须复用，应先由肉鸽适配层截获并标记 `rogueHandled`，确保不会同时执行主线奖励和肉鸽奖励。普通关卡的胜利事件则保持原有调用链不变。

### 19.8 UI 隔离

肉鸽入口、节点图、奖励卡和 Run 结算使用独立 GUI 类。普通关卡选择、战斗准备、经验结算和主线商店不应根据肉鸽状态改变布局或行为。肉鸽奖励界面关闭前必须屏蔽地图和战斗输入，避免重复点击导致双重确认。

## 20. 隔离验收用例

实现后至少执行以下测试：

| 用例 | 预期结果 |
| --- | --- |
| 从原关卡入口进入普通战斗 | 不创建 Run，不弹肉鸽卡牌，原经验/掉落不变 |
| 肉鸽击杀一个敌人 | 仅 Run 等级 +1，生成一组奖励队列 |
| 未确认卡牌时退出/断档 | 不获得未确认装备、技能或道具 |
| 肉鸽中购买恢复后回主线 | 主线金币、商店库存和角色正式 HP/SP 不被错误覆盖 |
| 肉鸽胜利后回到入口 | 临时物品按结算规则处理，世界配置恢复 |
| 肉鸽失败或主动放弃 | 与胜利一样执行清理，不残留 `active` 标志 |
| 读取普通存档 | 肉鸽状态关闭，普通关卡流程正常 |
| 重复触发战斗胜利回调 | 只产生一次 Run 结算和一次奖励 |
| 召唤物完成击杀 | 按归属规则只升级一次，不因死亡回调重复升级 |
| 读档恢复时缺失卡牌 ID | Run 可继续或安全转化，不影响普通存档读取 |

## 21. 主干装备和技能改动的影响策略

### 21.1 先区分三类数据

主干中的装备、技能和职业数据有三种不同性质，不能用同一种隔离方式处理：

1. **静态定义**：名称、图标、基础伤害、消耗、冷却、被动状态、装备属性和套装效果。
2. **运行时实例**：角色当前 HP/SP、技能 CD、技能等级、装备随机词条、耐久或强化层数。
3. **肉鸽规则**：卡池权重、品质、可出现层数、职业限制和重复转化规则。

当前项目的普通装备和技能大多通过 ID 解析模板，装备随机属性可以保存为副本实例；套装效果在 `ProjectGame` 中按当前装备 ID 和运行时逻辑计算。若肉鸽只保存 ID，就不能天然保证旧 Run 使用旧数值。

### 21.2 主干改动对不同 Run 的预期影响

| 改动 | 新开始的 Run | 已在进行的 Run | 已结算 Run |
| --- | --- | --- | --- |
| 新增武器/技能/卡牌 | 可以进入卡池，需通过权重和职业过滤 | 默认不插入已生成的奖励队列；下一次抽卡可选择是否加入 | 不影响已获得结果 |
| 调整基础伤害、属性、消耗、冷却 | 使用新数值 | **推荐继续使用创建 Run 时的规则版本** | 已结算结果不重算 |
| 修复明显战斗 Bug | 使用修复后逻辑 | 可立即生效，但要记录兼容版本 | 不回溯已完成统计 |
| 修改图标、名称、描述 | 使用新显示内容 | 可即时更新；若要求复盘一致则使用快照文本 | 不影响属性结果 |
| 修改套装效果或 `ProjectGame` 套装逻辑 | 使用新规则 | **推荐锁定 Run 规则快照** | 不重算历史结果 |
| 删除或重编号装备/技能 | 新 Run 不再抽取 | 不得让旧 Run 直接失效，应做 ID 映射或转化 | 结算记录保留历史名称 |

因此答案是：**主干改动可以影响肉鸽，但影响范围必须被明确控制。默认让新 Run 使用最新平衡，正在进行的 Run 使用创建时锁定的内容；不要让同一局在中途悄悄变强或变弱。**

### 21.3 推荐的 Run 版本锁定

创建 Run 时记录：

```text
contentVersion
cardPoolVersion
balanceVersion
skillDefinitionVersion
equipmentDefinitionVersion
rulesetSnapshot
```

卡牌第一次生成时，不只保存 `cardID`，还要保存其解析后的奖励快照：基础属性、技能效果、消耗、冷却、被动状态、套装模板 ID 和显示文本。玩家确认后再将该快照写入 Run 背包。

装备随机属性已经有副本装备支持，应继续使用副本实例；不能只保存装备模板 ID。技能需要采用同等策略：要么将技能转为 Run 专属副本，要么在 Run 中保存技能定义快照并由肉鸽战斗适配器读取，不能直接依赖实时主干技能模板。

### 21.4 哪些主干改动可以安全即时生效

可以即时生效的内容：

- UI 布局、图标清晰度和本地化文本修正。
- 不改变存档结构的性能优化。
- 不改变战斗结果的镜头、动画和音效修复。
- 明确标记为兼容性/安全修复的引擎 Bug 修复。

需要经过版本迁移或锁定的内容：

- 伤害公式、属性成长、技能范围、冷却和消耗。
- 装备基础属性、随机词条、套装效果和品质权重。
- 角色职业限制、技能解锁条件和卡池内容。
- 删除、重编号或改变数据结构的装备/技能。

### 21.5 主干背包和肉鸽背包的实现边界

现有 `ProjectPlayer.addEquipByInstance`、`learnSkillBySkillID` 和 `changeItemNumber` 面向玩家正常数据。肉鸽实现不能直接把它们当作默认发放路径，否则主干背包会被污染。应增加 Run 专用发放器：

```text
RogueRewardResolver
  -> RogueRunState.temporaryPackage
  -> 战斗角色副本/技能副本
  -> 结算时由白名单决定是否转入主线
```

如果首版为了复用接口暂时写入玩家副本，也必须在进入 Run 前做深拷贝，在 Run 结束时完整回滚，并测试穿戴装备、套装属性、技能 CD 和死亡状态；否则不视为真正隔离。

### 21.6 内容版本验收

实现后应至少验证：

- 创建 Run A，修改主干某件装备属性，再创建 Run B：B 使用新数值，A 仍使用锁定数值。
- 创建 Run 后删除一个卡牌引用：A 能继续读档，缺失内容按迁移规则转化。
- 修改套装效果：普通关卡使用新效果，旧 Run 不发生无提示变化。
- 更新技能图标/名称：不会改变已保存技能的伤害和冷却。
- 主干新增卡牌：不会插入已经显示但尚未确认的奖励队列。

## 22. 主干新增内容如何被肉鸽调用

肉鸽不应维护一份“当前装备/技能/职业/角色的固定 ID 白名单”。主干数据库新增内容后，只要符合数据契约和肉鸽标签，新开始的 Run 就可以自动发现并调用。这样新增内容只需要登记一次，不需要每次再手工修改肉鸽脚本。

### 22.1 新增技能和装备

新增技能、装备继续登记到项目现有技能/装备数据表，并在肉鸽卡池适配层动态扫描。卡池生成时执行：

```text
读取主干数据列表
  -> 过滤禁用/剧情专用/敌方专用数据
  -> 检查职业、武器部位、技能类型和品质
  -> 读取 rogueEnabled、rogueWeight、rogueMinFloor 等标签
  -> 生成候选卡
```

建议为技能和装备增加以下肉鸽元数据；若项目数据结构不适合直接扩展，可在 `customRogueCardData` 中建立同 ID 的覆盖记录：

```text
rogueEnabled: boolean
rogueType: weapon | equipment | activeSkill | passiveSkill | consumable
rogueWeight: number
rogueMinFloor: number
rogueMaxFloor: number
rogueAllowedClassIDs: number[]
rogueDuplicatePolicy: upgrade | convert | forbid
rogueBalanceGroup: string
```

未标记的新内容默认不进入肉鸽卡池，但仍可在普通关卡正常使用。这样可以先把数据加入数据库，再通过标签决定何时进入肉鸽。

### 22.2 新增职业

新增职业只要在当前职业/角色模块中完成正式登记，就可以被肉鸽识别。需要额外确认：

- 职业 ID 唯一且不会复用旧 ID。
- 成长表、基础技能、可装备部位和职业标签完整。
- `rogueAllowed` 或等价标签已开启。
- 有初始武器/技能池映射。
- 没有依赖主线剧情开关才能初始化的关键技能。

肉鸽入口的队伍选择应从当前角色数据库动态读取，而不是复制旧的初始队伍 JSON。新职业默认可以作为可选角色加入新 Run；若暂不平衡，只需关闭 `rogueAllowed`，不必修改肉鸽核心代码。

### 22.3 新增角色和召唤物

新增玩家角色、友军 NPC、召唤物和 Boss 需要区分用途：

- `playerUsable + rogueAllowed`：可作为肉鸽初始角色或卡牌奖励目标。
- `npcOnly`：可以作为事件/商人/友军对象出现，但不进入玩家角色选择。
- `summonOnly`：作为技能产生的战斗单位，奖励归属由召唤者决定。
- `bossOnly`：只进入 Boss 池，不进入普通角色或卡牌池。

角色加入肉鸽前需要通过出生点、战斗阵营、技能引用、装备部位和死亡处理检查。新增角色的立绘、行走图和战斗资源缺失时，应在卡池校验阶段排除，不能等到战斗中才报错。

### 22.4 新内容与版本锁定的兼容方式

版本锁定不等于禁止新增内容。推荐采用以下规则：

- 新 Run：扫描当前主干数据库，获得全部符合标签的新内容。
- 进行中的 Run：不修改已生成的卡牌和奖励队列；到达“下一节点”时，可按兼容策略选择是否刷新卡池版本。
- 严格模式：整个 Run 固定创建时的卡池版本，最稳定。
- 宽松模式：新内容只允许出现在尚未生成的奖励中，不改变已获得内容。

首版建议使用严格模式。主干新增内容会从下一局开始生效，正在进行的 Run 不会突然出现新技能或新装备；这样最容易复现问题，也不会破坏玩家已经规划好的构筑。

### 22.5 数据校验与失败降级

每次创建 Run 和每次构建卡池前执行数据校验：

- ID 存在且类型正确。
- 图标、名称和描述可读取。
- 装备部位、职业限制和技能目标类型合法。
- 技能效果引用的状态、动画和公共事件存在。
- 角色成长表、初始技能和战斗资源完整。
- 肉鸽数值位于允许的品质/平衡组范围。

校验失败的内容从肉鸽候选池排除，并记录诊断信息；不能阻塞普通关卡，也不能让整个 Run 无法读档。若某张已获得卡牌在后续版本中被删除，则按 `duplicatePolicy` 转化为金币、材料或同品质替代卡。

### 22.6 最终调用边界

肉鸽调用的是主干的“数据定义”，但使用的是自己的“运行时容器”：

```text
主干数据库：技能/装备/职业/角色模板
        ↓ 动态扫描 + 标签过滤 + 版本校验
肉鸽卡池：候选定义快照
        ↓ 玩家确认
Run 临时角色/装备/技能副本
        ↓ Run 结束
清理或按白名单结算到主线
```

因此，数据库新增内容不需要重复制作一套肉鸽专用技能或装备；只需要符合统一登记、标签、资源和版本规则，即可被肉鸽正常调用。

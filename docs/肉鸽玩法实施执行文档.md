# 肉鸽玩法实施执行文档

## 1. 文档目的

本文档合并《肉鸽玩法设计方案》和《肉鸽玩法执行交接》，并以 2026-08-20 的项目代码和数据为准，作为肉鸽玩法第一阶段的实施、联调和验收依据。

第一阶段目标是完成一个可运行、可保存、可退出且不污染普通玩法的垂直切片。除非另行确认，本阶段不提前制作复杂随机路线、大量美术资源、永久解锁、多 Boss 词缀或完整商人经济。

## 2. 当前项目事实

项目是基于 Game Creator 的 TypeScript/JSON 单机 SRPG：

- 业务源码位于 `Game/game/`，TypeScript 编译目标为 ES5。
- UI、场景、公共事件和模块数据位于 `asset/json/`。
- 浏览器实际加载 `out/Game.js`，源码改动后需要重新编译。
- `Game/tsconfig.json` 使用显式 `files` 列表，新增脚本必须登记。
- 已建立 `Game/game/project/rogue/` 运行时、`Game/game/project/ui/rogue/` 界面脚本和固定八节点垂直切片；当前实施状态见第 15 节。
- UI 38 是“演示-关卡选择”，当前包含四张关卡卡片，没有项目层 `GUI_38.ts`。
- 场景列表除文档原有内容外，已新增场景 15“关卡5-边境林道伏击”和场景 16“关卡6-Arkanos庭院”。

## 3. 已确定的产品规则

### 3.1 模式与流程

- 肉鸽是独立玩法入口，普通关卡不会创建或恢复 Run。
- 第一阶段使用固定八关流程：战斗 A -> 战斗 B -> 林道废墟 -> 庭院回廊 -> 腐化祭坛 -> Boss I -> Boss II -> Boss III。
- 后续阶段再加入商人、休整、随机节点、地图池和 Boss 池。
- 首版为纯局内 Run，临时金币、装备、技能、被动、道具和属性默认不带回主线。
- Run 结束、失败或放弃后清理临时数据；永久带出只能通过后续白名单结算模块实现。

### 3.2 击杀与奖励

- 每个有效敌方单位死亡，`runLevel +1`，且实际击杀角色在 Run 隔离副本中精确升 1 级；同一个死亡目标只结算一次。
- 每次有效击杀独立生成一组三张候选卡，并加入 `rewardQueue`。
- 三选一不能在 `die` 回调中直接打开，必须等待攻击、反击、连击、死亡动画及当前行动奖励链全部完成。
- 多杀时保留每个敌人的独立奖励组，按进入队列的顺序逐组展示。
- 召唤物、反伤、状态、地形和环境击杀必须解析到玩家方 `killOwner`；无法确认归属的环境击杀不升级、不发卡。
- 达到 Run 等级上限后，将升级转换为金币、恢复或下一次奖励品质提升，具体数值后续配置。

### 3.3 跨图状态

- 普通小图之间继承 Run HP/SP，不自动回满。
- Run 开始时保存 `WorldData.fullStateWhenBattleStart` 原值，并在 Run 期间设为 `false`。
- 胜利、失败、放弃、普通存档读取、Run 存档损坏和异常恢复都必须执行幂等恢复。
- 普通角色正式等级、经验、主线金币、背包、技能和剧情开关不得被 Run 直接修改。

### 3.4 内容版本

- 新 Run 扫描当前主干数据中明确允许进入肉鸽的技能、装备、职业和角色。
- 未标记内容不进入肉鸽卡池，也不影响普通玩法。
- 进行中的 Run 锁定创建时的内容版本和已生成奖励快照。
- 装备保存副本实例；技能和即时效果保存解析后的定义快照，不能只保存模板 ID 后读取最新主干数值。

## 4. 两项强制实现约束

### 4.1 多杀不能依赖 `hitReward` 计数

现有 `GameBattleData.hitReward` 是一次行动共享的累计容器。范围技能、连击或反击造成多个敌人死亡时，金币、经验、道具和装备会合并，无法据此还原每个死亡目标。

因此必须采用两阶段处理：

```text
GameBattleData.die
  -> 确认目标为敌方
  -> 解析 killOwner
  -> 使用死亡目标唯一 ID 去重
  -> runLevel +1
  -> 为该死亡目标独立生成 3 张卡
  -> 将一组候选写入 rewardQueue
  -> 不在此处打开 UI

GameBattleAction.calcCurrentActionReward 完成
  -> 检查 RogueRunManager.active
  -> 若 rewardQueue 非空，锁定战斗输入
  -> GUI_RogueReward 逐组展示
  -> 队列清空后恢复原行动结束流程
```

实现要求：

- `RogueKillProgress` 监听或接收每次死亡，而不是读取合并后的 `hitReward` 数量。
- 每组奖励保存 `rewardGroupID`、`deadBattlerUID`、`killOwnerUID`、生成种子、三张卡快照和确认状态。
- `processedDeathIDs` 防止强制死亡、状态页切换、读档恢复或重复回调导致重复结算。
- 奖励 UI 的完成回调必须接回原来的 `endAction`/战斗完成流程，不能令 `SyncTask` 永久等待。
- 即使肉鸽不发放普通掉落，也必须重置原有 `hitReward` 和 `dropEXPFragmentCount`，避免奖励泄漏到下一次普通结算。

### 4.2 场景 15、16 只能作为候选模板评估

场景 15“边境林道伏击”和场景 16“Arkanos庭院”是交接文档完成后新增的内容。它们可以用于评估地图尺寸、出生点、美术资源和战斗节奏，但不能直接作为肉鸽节点使用。

评估步骤：

1. 检查场景进入、离开、战斗开始、胜负和剧情事件。
2. 检查主线变量、独立开关、任务条件和固定角色引用。
3. 检查玩家/敌人出生点、移动可达性、镜头范围和移动端遮挡。
4. 检查场景对象是否依赖主线前置状态。
5. 将适合的地块、碰撞和美术层复制到新的肉鸽专用场景 ID。
6. 在新场景上重新建立肉鸽进入事件、敌人组、胜负条件和离开节点。

第一阶段建立独立的八个肉鸽场景。不得直接修改或复用带剧情事件的主线场景 ID。

建议新增目录 `Game/game/project/rogue/`，保持以下职责：

第一阶段至少保存：

```text

balanceVersion
floorIndex
currentNodeID

partySnapshots

lastTransactionID
```

`rewardQueue` 每项至少包含：

```text
rewardGroupID
deadBattlerUID
killOwnerUID
seed
cards[3]
selectedCardID
status: pending | showing | confirmed
createdTransactionID
confirmedTransactionID
```

每张卡快照至少包含：

```text
cardID
type
quality
name
description
iconID
sourceDefinitionID
definitionVersion
effectSnapshot
duplicatePolicy
```

存档恢复要求：

- `pending` 奖励继续排队。
- `showing` 奖励恢复为 `pending`，不得视为已领取。
- `confirmed` 奖励根据事务 ID 保证不会重复发放。
- 缺失或已删除的定义按迁移表替换，无法替换时转换为 Run 金币或同品质替代奖励。
- Run 数据损坏不能影响普通存档读取。

## 7. 卡池规则

首版卡牌类型：武器、其他装备、主动技能、被动技能、消耗品、即时强化。

主干内容通过以下元数据进入卡池：

```text
rogueEnabled
rogueType
rogueWeight
rogueMinFloor
rogueMaxFloor
rogueAllowedClassIDs
rogueDuplicatePolicy
rogueBalanceGroup
```

若不适合扩展原模块数据，则在 `customRogueCardData` 中按主干 ID 建立覆盖记录。未配置 `rogueEnabled` 的内容默认排除。

抽卡顺序：

1. 使用 Run 种子、层数、击杀序号和卡池版本派生本次种子。
2. 扫描并校验当前版本允许的候选定义。
3. 按职业、装备部位、资源完整性、最低层数和重复策略过滤。
4. 按层数决定品质权重。
5. 优先抽取不同类型的三张卡。
6. 候选不足时允许同类型，但禁止完全相同的实例。
7. 保存三张解析后快照，再进入 `rewardQueue`。

## 11. 代码挂点策略

### 11.1 `GameBattleData.die`

在死亡成立、目标状态可读取后通知 `RogueKillProgress`。新增逻辑必须由 `RogueRunManager.active` 保护。不要在这里展示 UI，不要阻塞死亡清理。

### 11.2 `dropRecordByDie` 与 `calcHitReward`

肉鸽激活时不得将普通奖励写入 `ProjectPlayer`。具体可采用：

- 在 `dropRecordByDie` 前分流，肉鸽完全跳过普通掉落累计；或
- 允许暂存但在 `calcHitReward` 最前面清空并走肉鸽完成回调。

首选前者，边界更清晰。无论采用哪种方式，都必须正确清理共享计数器。

### 11.3 `GameBattleAction.calcCurrentActionReward`

保留原 `SyncTask` 顺序。在普通模式完全走原逻辑；肉鸽模式完成必要清理后调用奖励队列展示器，待队列清空才执行原来的 `endAction` 或 `onFin`。

### 11.4 `GameBattle.checkBattleIsComplete`

胜负结果进入 `14022` 前后增加肉鸽事务保护。最后一击产生的奖励队列必须先处理，战斗胜利节点只能提交一次。

### 11.5 `GameGate` 与存档事件

场景加载不新增平行实现。Run 状态只监听场景门阶段并在进入完成后初始化节点。普通存档恢复前强制校验模式，继续 Run 时才恢复肉鸽状态。

## 12. 必须通过的验收用例

| 用例 | 预期结果 |
| --- | --- |
| 普通入口进入普通战斗 | 不创建 Run，不弹卡，原经验和掉落不变 |
| 肉鸽击杀一个敌人 | `runLevel +1`，击杀角色升 1 级，生成一组奖励，主线快照不变 |
| 范围攻击击杀三个敌人 | `runLevel +3`，各击杀归属角色按次数升级，生成三组互相独立并串行展示的三选一 |
| 反击击杀敌人 | 归属到反击者所属玩家角色，只结算一次 |
| 召唤物击杀敌人 | 归属到召唤者；无召唤者记录时不结算 |
| DOT/状态击杀敌人 | 能解析来源时结算，无法解析时不结算 |
| 同一目标重复触发 `die` | `processedDeathIDs` 阻止重复升级和发卡 |
| 未确认卡牌时存档/退出 | 不获得奖励，恢复后仍为待选择状态 |
| 已确认奖励后重复恢复 | 事务 ID 阻止重复发放 |
| 最后一击同时结束战斗 | 先完成最后一组奖励，再推进胜利节点，胜利只提交一次 |
| Run 中跨图 | HP/SP、临时构筑和队列状态正确继承 |
| Run 失败或放弃 | `active=false`，世界规则恢复，临时容器清理 |
| 普通存档读取 | 清理肉鸽残留，不读取 Run 临时背包 |
| Run 快照损坏 | 普通存档仍可读取，可放弃 Run 或执行降级 |
| 修改主干装备后创建新 Run | 新 Run 使用新版本，旧 Run 使用已保存快照 |
| 新增带肉鸽标签的内容 | 仅新 Run 可扫描到，未标记内容不出现 |
| 重复触发 `14022` | 节点和结算不重复推进 |
| 场景 15、16 保持主线进入 | 肉鸽开发没有改变其原事件和流程 |

## 13. 第一阶段完成定义

只有同时满足以下条件，第一阶段才算完成：

- 普通关卡进入、战斗、奖励、胜负和存读档回归通过。
- UI 38 的肉鸽入口可用，原四个入口行为不变。
- Run 支持开始、继续、失败、完成和放弃。
- Run 快照具有版本、种子、节点、临时容器和事务字段。
- 每个有效敌人独立升级和生成奖励，多杀不会合并或漏发。
- 三选一只在完整行动链结束后展示。
- 所有奖励只进入 Run 临时容器。
- 固定五张普通战斗图和三张 Boss 图可以完整通关。
- 所有退出路径都能幂等恢复世界规则。
- 新主干内容可以通过标签进入新 Run，旧 Run 保持快照一致。
- TypeScript 构建通过，桌面、触屏和手柄基础交互通过。

## 14. 后续阶段

第一阶段稳定后，按以下顺序扩展：

1. 随机节点、地图池、商人和休整。
2. 品质曲线、重复转化、Run 商店库存和价格种子。
3. 三个以上 Boss、精英敌人、被动层数和临时词缀。
4. 永久解锁和白名单带出结算。
5. 更完整的移动端适配、动画、美术和性能优化。

上述扩展不得破坏“共用底层引擎、独立玩法状态”的隔离原则。
